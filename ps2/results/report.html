Flatland

How we stopped an attacker from walking across a flat company network, and how we can prove it
Problem Statement 2: Network segmentation and firewall design
Secure Networks Hackathon, 21 November 2026

A plain-language report with the real outputs from our lab

1. The story in one minute

Imagine a company office with no walls and no locked doors. The receptionist, the accountant, the safe and the filing room are all in one big room. If a stranger walks in and sits at any desk, they can walk to the safe.

That is a flat network: every computer can talk to every other computer. If an attacker takes over just one ordinary workstation, they can reach the database in minutes.

Our job was to prove the problem, then rebuild the office with rooms and locked doors (this is called segmentation) so the attack fails, without stopping anyone from doing their real work.

55doors open on the flat network (47 of them not needed)
8doors open after: exactly the 8 the business needs
8 of 8business tasks still work
100%of unnecessary paths removed
In plain words: we built a fake company network on one laptop, attacked it, fixed it, attacked it again, and then used a checker to show that nothing is reachable except what the business needs.

2. Words you will see (in plain English)

TermWhat it means
Network / hostA network is computers connected together. A host is one computer on it.
PortA numbered door on a computer. Each service listens on its own door: 22 is remote login (SSH), 443 is secure web, 445 is shared folders (SMB), 5432 is the database.
FirewallA bouncer that decides which connections may pass. Ours is nftables, built into Linux.
RouterThe machine that connects separate networks and passes traffic between them. Ours is also where the main firewall sits.
Subnet / zoneA separate section of the network. We made four zones: user, DMZ (public-facing), server and management.
Default denyThe rule 'block everything unless it is on the allowed list'. The opposite is 'allow everything unless banned', which is how flat networks behave.
Business flowA connection the company genuinely needs, for example the web server talking to the app server on port 8080. We have 8.
Micro-segmentationA small firewall on each computer, so even a computer in the same room cannot talk to it unless allowed.
Egress filteringControlling what a machine can send out. It stops a hacked machine from phoning home to the attacker.
Rate limitingLimiting how many new connections can be tried per minute. It slows password guessing.
MITRE ATT&CKA public catalogue of attacker techniques with ID numbers (for example T1046 is port scanning). We use it to name what the attacker did.
D3FENDThe matching catalogue of defensive techniques.

The big idea: the policy file is the single source of truth

Instead of typing firewall rules by hand (easy to get wrong), we wrote one short file, policy.yaml, that lists the 8 connections the business needs. A program (gen.py) reads it and generates everything else: the lab setup, the router rules, the host firewalls, the tests and the tables in this report. Change one line and everything updates.

  1. policy.yaml: zones, addresses and the 8 allowed connections.
  2. gen.py: creates the firewall rules, lab files and business tests from the policy.
  3. Lab: the flat network (before) and the segmented network with a router (after).
  4. Proof harness: tests all 180 combinations of source machine, destination machine and port, from inside the machines.
Why this matters: most teams write rules once and hope. We can prove the network matches the policy, and a judge can change a rule and see the result in one command.

5. Seeing the problem: the reachability map

To measure the problem, a checker logs into each machine and tries to connect to every other machine on six common ports: 6 sources x 5 destinations x 6 ports = 180 tries. Each try is one square on the map below.

  • Green: connection works and the business needs it.
  • Red: connection works but the business does not need it. This is the attacker's playground.
  • Grey: connection is blocked.
How to read it: before, 47 red squares are things an attacker can use. After, there are zero red squares and the 8 green business flows are untouched.

7. How it is enforced: four layers

We stack four locks and test each one.

Layer 1: the router says 'no' by default

The router's firewall starts from policy drop: anything not on the list is thrown away. Each business flow gets one rule. Here are the real first rules (generated/router.nft):

Real file: router rules (excerpt)
flush ruleset

table inet ps2 {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif lo accept
  }
  chain forward {
    type filter hook forward priority 0; policy drop;
    ct state invalid drop
    ct state established,related accept
    ip saddr 10.10.10.10 ip daddr 10.10.20.10 tcp dport 443 ct state new accept comment "F1 ws->web:443"
    ip saddr 10.10.20.10 ip daddr 10.10.30.10 tcp dport 8080 ct state new accept comment "F2 web->app:8080"
    ip saddr 10.10.30.10 ip daddr 10.10.30.11 tcp dport 5432 ct state new accept comment "F3 app->db:5432"
    ip saddr 10.10.30.10 ip daddr 10.10.30.12 tcp dport 445 ct state new accept comment "F4 app->files:445"
    ip saddr 10.10.40.10 ip daddr 10.10.20.10 tcp dport 22 ct state new limit rate 20/minute burst 20 packets accept comment "F5 jump->web:22"
    ip saddr 10.10.40.10 ip daddr 10.10.30.10 tcp dport 22 ct state new limit rate 20/minute burst 20 packets accept comment "F6 jump->app:22"
    ip saddr 10.10.40.10 ip daddr 10.10.30.11 tcp dport 22 ct state new limit rate 20/minute burst 20 packets accept comment "F7 jump->db:22"
    ip saddr 10.10.40.10 ip daddr 10.10.30.12 tcp dport 22 ct state new limit rate 20/minute burst 20 packets accept comment "F8 jump->files:22"
    # log what is dropped, per source zone (read with: tcpdump -i nflog:1)
    ip saddr 10.10.10.0/24 limit rate 100/second burst 200 packets log prefix "PS2-DROP zone=user " group 1

Layer 2: every computer has its own firewall

Even if a router rule were wrong, each machine only accepts the connections listed for it. This is the database's own firewall: only the app may connect on 5432 and only the jump host on 22.

Real file: database host firewall
flush ruleset

table inet hostfw {
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ct state established,related accept
    ip saddr 10.10.30.10 tcp dport 5432 ct state new accept comment "F3"
    ip saddr 10.10.40.10 tcp dport 22 ct state new limit rate 20/minute burst 20 packets accept comment "F7"
    counter drop
  }
  chain output {
    type filter hook output priority 0; policy drop;
    oif lo accept
    ct state established,related accept
    counter drop  # egress filtering: no outbound callbacks from this host
  }
}

Layers 3 and 4: egress filtering and rate limiting

Egress: the database may not start outbound connections, and the server zone may not call into the user zone, so a hacked server cannot phone home. Rate limit: management logins are capped at 20 new connections per minute, which makes password guessing slow and noisy.

In plain words: the attacker knocked on doors it was never allowed to open. The router refused 105 knocks and recorded exactly who tried what. That log is what a security team would investigate, and it maps directly to ATT&CK: scanning (T1046), mapping the network (T1018), SSH attempts (T1021.004) and SMB attempts (T1021.002).

11. Can we trust our own checker? We break the network on purpose

A test that always says 'PASS' is worthless. So we deliberately made a mistake and checked that the checker noticed.

StepResultWhat happened
S1PASSrouter had a wrong rule but the db host firewall still blocked it (defense in depth)
S2PASSharness detected the injected hole (1 unauthorized path: ws -> db:5432)
S3PASSrulesets restored, proof passes again (0 unauthorized)
  1. S1: we added one wrong rule on the router that let the workstation reach the database. The database's own firewall still blocked it. That is why we use two layers.
  2. S2: we also added the matching hole on the database firewall. Now the network really was wrong, and the checker caught it.
  3. S3: we restored the rules and the checker passed again.
Real output: negative control
S1|PASS|router had a wrong rule but the db host firewall still blocked it (defense in depth)
S2|PASS|harness detected the injected hole (1 unauthorized path: ws -> db:5432)
S3|PASS|rulesets restored, proof passes again (0 unauthorized)

Honest note: segmentation does not make a machine unhackable. It limits how far a hack can spread (the 'blast radius') and makes every extra step visible and noisy.

16. Limits and what we would do next

  • The checker tests TCP on six ports. UDP and IPv6 are not tested yet.
  • Allowed connections can still be abused, for example SSH from the jump host. Rate limiting slows this but does not remove it.
  • The weak password Password123 exists only in the lab, on purpose, so the attacks work.
  • Next: test UDP and IPv6, alert on drops in real time, and run the proof automatically whenever the policy changes so a mistake cannot ship.
